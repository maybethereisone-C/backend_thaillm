FahMai Agent — Inference Pipeline

How the ReAct agent reads the database and produces an answer · max 8 steps · typhoon-s-thaillm-8b-instruct

End-to-End Flow

❓
Question received
Thai-language question from scoring server. Sanitized: null bytes and zero-width characters stripped before entering the agent.
📋
System prompt built
SYSTEM_TMPL injected with full DuckDB schema + value hints (exact WHERE-clause literals). REFUSAL_GUIDE appended — fixed-phrase injection patterns handled at prompt level. Messages: [system, user("QUESTION: …")]
↓
ReAct loop — repeat up to 8 steps
🧠
LLM call → raw action text
POST /chat/completions → model outputs one JSON action object embedded in plain text. max_tokens=2500, temperature=0.0.
🔍
Parse action
Extract first balanced {…} from raw text. Tolerate trailing prose, multiple objects. Retry with whitespace-collapsed JSON on parse failure.
⚙️
Execute tool against DuckDB
See tool table below. Result truncated to 3000 chars if large.
💬
Build OBSERVATION nudge
If rows found → "You now have the data. Output final NOW."
If error → "Fix exact table/column names from schema."
If repeated action → "You already ran this — output final."
Append [assistant: raw, user: nudge] to messages.
↑ loop back to LLM call  ·  until action = "final" or 8 steps exhausted ↓
↓
🏁
Forced finalization (if loop exhausted)
Inject: "Stop searching. Reply with ONLY the final answer in plain text." One last LLM call. If JSON leaks through → render last good observation. If empty → Thai fallback string.
🧹
Post-process answer
post_process(answer) — conservative cleanup only:
Strip JSON/action leakage ({"action":…}), filler phrases, leading/trailing whitespace.
Does NOT reformat numbers or alter factual content.
✅
Return answer + trace
(answer: str, token_count: int, trace: JSON) — trace is every step's action and arg, written to audit trail {id}.txt.

Database Tools

sql DuckDB
SELECT … FROM dim_*/fact_*
Read-only query. Returns {rows, row_count} or {error}. Use for any count/sum/aggregation/lookup.
claim_lookup doc layer
domain: DQ3 | DQ4 | E2 | E9 | L1 | L2 | CEO
Search document chunks by planted-incident domain code. Optional date_from / date_to filter.
doc_search doc layer
query: keywords or IDs
RAG search over docs_chat_messages (LINE WORKS chat logs, narrative memos). Optional channel + date filters.
policy_resolver point-in-time
policy_variable + as_of_date
Looks up DIM_POLICY_VERSION for the value in effect on a given date. Use for: return window, refund threshold, free shipping, point earning rate.
kb_search KB manual
query: keywords
Full-text search over L1 customer-service KB manuals. Use for policy wording, membership tiers, warranty terms, company founding.
final terminate
answer: "exact value"
Ends the loop immediately. act["answer"] becomes the response. Should contain exact numbers/IDs asked for.

Critical Query Rules

RuleDetail
Date axis default Use business_event_date for year/month/quarter windows. Use posting_date only when question explicitly mentions GL posting / month-end close.
FACT_VENDOR_PAYMENT NET-30 invoices — posting_date lags business_event_date by ~28 days (~95% of rows cross calendar months). Always filter by business_event_date.
Brand filter dim_product.brand_family values are English only: SaiFah, NovaTech, FahMai, ArcWave, Dawn, WatchKit. "ฟ้าใหม่" = company name — never filter brand_family for it. FACT_SALES, DIM_CUSTOMER, etc. have no brand_family column.
CEO identity Two rows in dim_employee have position_title='CEO'. Naret Vision (EMP-L3-00013) is CEO after 2025-01-15. Always verify with sql on dim_employee before stating any name/role.
Ground truth Database is ground truth. If a question asserts a false fact (wrong price, wrong role), report what the database says, not the question premise.
Repeated action guard Actions are hashed. If the same JSON action is seen twice, the nudge forces immediate final output using results already gathered.
